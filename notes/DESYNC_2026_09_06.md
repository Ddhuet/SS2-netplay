# Shop interaction desync: September 6 capture

User reports recurrence while interacting with shops after completing the first
map. Player 1 was the host (capture seat 0); player 2 was the guest (seat 1).
User has manually verified in-game saving/loading. No automated save persistence
check was performed for this investigation.

Original evidence is preserved under recordings/9-6-2026-desync-logs. Both capture
folders are sufficient for the comparisons below. The nonempty supplied session
text actually identifies CONNECTED seat=0 and the same boundary 65760 failure;
the other supplied session text is empty. No additional session text is needed
for this stage. The captures contain private startup save images.

## Verified comparisons

- ROM, executable, RTC, initial aggregate state and both startup save hashes agree.
- All 67 component byte arrays agree at initial boundary 0 and matched boundary
  65700. Across all 73,432 shared component hash entries (1,096 checkpoints), the
  only mismatch is core/1/state/wram at boundary 65760.
- At 65760, 23 bytes differ inside offsets 0x31f3c through 0x31f53, corresponding
  to GBA EWRAM addresses 0x02031f3c through 0x02031f53. All other captured
  components match, including both CPUs, timing, link state and save-memory.
- The host's submitted inputs match the guest's received inputs for all 65,763
  shared sequences; the guest's submitted inputs match the host's received inputs
  for all 65,764 shared sequences. No duplicate or missing received sequences.
- Both peers report the same first mismatching settled boundary, 65760. The host
  stopped at frontier 65767 (2,608 corrections, max depth 7); guest frontier 65766
  (3,141 corrections, max depth 6).

This is a real RAM-byte difference, not evidence of different startup files or
corrupted/missing input payloads. Its gameplay significance and the first divergent
instruction are not yet established. Do not mask these bytes or weaken hashing.

## Reproducible tools

app/compare-captures.py takes the host and guest capture directory paths and
prints bounded input/hash/byte comparison counts. Full report is kept privately
at recordings/9-6-2026-capture-comparison.txt.

app/examples/capture_baseline.rs reconstructs both input streams from one capture,
validates ROM/save hashes and the initial state, then runs a direct linked baseline
without rollback. It compares every recorded component checkpoint and writes only
mismatching components to a new output directory. It never writes playable saves.
Build using the same Cargo environment as the harness, with --release --example
capture_baseline. Arguments: ROM CAPTURE NEW_OUTPUT_DIRECTORY. This is a separate
diagnostic executable, not the exact captured EXE; build identity is noted in its
report. Existing emulator/session sources are unchanged.

With optional --schedule, the tool instead replays the captured order of local
advances and remote input arrivals (including tick advantage) through Session.
The observer revokes observations on rewind and compares only actually settled
checkpoints. Audio output buffers are drained; this is not a wall-clock or UI
replay. No network connection is needed.

## Direct baseline result

The direct no-rollback replay matched the host's captured component hashes at
every boundary through 65760, including the failure boundary. Therefore the guest
RAM is the outlier relative to this baseline. This validates startup fixtures and
input reconstruction through the reported shop interaction without another manual
playthrough. Report: recordings/9-6-2026-baseline-host-quiet/report.txt.

## Recorded guest schedule result

The offline Session replay of the guest's recorded ADVANCE/Input arrival order

## September 7 restore isolation

A direct save at 65728, one direct reference step, load of that same snapshot and
identical next input reproduces the 65729 discrepancy. Wrong predictions are not
required. The immediate restore changes timing queue root/reroot representation
and some live interrupt diagnostic scratch fields. Explicitly restoring the
original queue representation (either core or both), CPU shifter scratch, last
jump, or all of those together does NOT eliminate the next-tick RAM difference.
See recordings/9-7-2026-intervention/report.txt. These failed interventions were
confined to the offline example; no corresponding emulator fix was applied.

The additional live memory-access comparison found no difference in selected CPU
active-region/mask/wait-cycle/access-source fields, memory prefetch and waitstate
tables, DMA-active fields or bus value. Explicitly copying those runtime fields
also fails to fix the discrepancy. See recordings/9-7-2026-memory. A suggested
WAITCNT omission was ruled out by source inspection: WAITCNT at 0x204 is NOT in
the write-special register table, so GBAIODeserialize invokes GBAIOWrite and
GBAAdjustWaitstates for it.

Next diagnostic: temporary ARM instruction tracing, restricted to core 1 and
only tick 65729, comparing the direct and restored execution. Its raw fixed-width
records contain 16 GPRs, CPSR, both prefetched instructions, cycle count, next
event deadline and execution mode (22 u32 values). The hook is diagnostic only
and must be removed before a player build is distributed.

## Root cause and correction

The first timing divergence occurs at core 1 instruction 73 of tick 65729:
BIOS PC 0x2f4, `stmlt r1!, {r3-r10}`, writing zeroes to VRAM starting at
0x0600e3c0. Identical operands take 17 cycles directly and 24 after restoration.
At instruction 833 the resulting timing shift changes where an IRQ interrupts
the BIOS copy loop. That explains the differing stack/RAM residue despite CPU
registers reconverging at the later settled boundary.

Both cores' original video.stallMask values were zero (VBlank; core 0 VCOUNT160,
core 1 VCOUNT161). GBAVideoDeserialize reconstructs mode-2 video state with an
active-display contention mask even during VBlank, producing 255 on both cores.
Its reconstruction also reads live background registers before IO restoration,
and cannot recover a mask latched before a mid-scanline register change. Simply
reordering IO writes is therefore insufficient for exact rollback.

Diagnostic intervention copying ONLY the saved stallMask back after Link.load
eliminated ALL next-tick component differences. Previous queue/scratch/memory
interventions did not. Evidence: recordings/9-7-2026-video/report.txt.

Fix: Link's generic Snapshot now preserves each core's exact video contention
mask and restores it after core/FIFO/DMA deserialization. The snapshot digest
and canonical diagnostics include the mask (`core/N/video/contention`). This
adds two components for a two-core link. Historical offline comparison tools
omit only those explicitly new components when checking old capture hashes;
direct-versus-rollback comparisons continue to include them.

Two synthetic regressions failed before the change and pass afterward: VBlank
must retain zero contention, and HDraw must retain its latched mask despite
future or mid-line background-register writes. No ROM or personal save fixture
is required for these tests. Temporary instruction tracing was removed from
the emulator source before building the updated portable harness. Diagnostic
trace source and outputs remain privately under recordings/.
